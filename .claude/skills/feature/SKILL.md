# 機能を 1 本の PR として仕上げる

引数で受け取った内容（`$ARGUMENTS`）を、`AGENTS.md` の規約に沿って実装し PR にする。
**途中の工程を飛ばさない。** 特にテスト設計と監査は、飛ばすと後で必ず高くつく。

## 0. 前提を確かめる

`AGENTS.md` を読む（構成・規約・検証コマンド・ブランチ名の付け方）。

`git status` で現在地を確認する。未コミットの変更があるなら、それを先に片付けるか
別ブランチに退避するかをユーザーに確認する。

## 1. origin と同期してブランチを切る

既定ブランチ（`.claude/harness.json` の `defaultBranch`、通常 `main`）から切る。

```powershell
git fetch origin --prune
git switch main
git pull --ff-only
git switch -c <AGENTS.md の命名規則に沿ったブランチ名>
```

> `origin/main` から切ること。前の作業ブランチから枝分かれさせない。

## 2. 対象を読む

実装に入る前に、変更する範囲のコードを読む。既にある関数や書き方を使えるなら、
新しく作らない。

## 3. テストを設計させる

`test-designer` エージェントに、これから実装する内容と読んだファイルを渡して
テスト仕様を作らせる。

返ってきた「落とし穴」と「テストしやすさの問題」を読み、
**必要なら実装方針のほうを変える**（時刻や乱数を注入可能にする、判断ロジックを
フレームワークから切り離して単体でテストできる形にする、など）。

## 4. 実装する

`AGENTS.md` の「規約」に従う。

## 5. テストを書く

3 で設計した項目のうち「自動」のものを実装する。置き場所と書き方は `AGENTS.md` の
「テスト方針」に従う。各テストには日本語で「何を保証するのか」の説明を付ける。
この説明はテスト仕様書（`<reportsDir>/test-spec.md`）にそのまま載り、人間がテストを確認する窓口になる。

- 時刻・乱数は固定する
- 期待値は実装と同じ式で計算せず、定数でベタ書きする
- 外部サービスを実際に呼ぶテストは既定で実行しない（手動確認用にゲートする）

「手動」の項目は、PR に書く確認手順として控えておく。

## 6. テストを監査させる

`test-auditor` エージェントに、書いたテストと対象の実装を渡す。

**不合格なら直す。** 「指摘は受けたが今回はこのまま」は無し。
監査を通せないテストは、壊れたときに落ちない。

## 7. コミットする

意味のある単位で分ける。1 コミット 1 目的。メッセージの書式は `AGENTS.md` に従う。

## 8. 検証する

`test-runner` エージェントに `.\.claude\scripts\run-checks.ps1` を実行させる。

落ちたら原因を直す。**テストを緩めて通してはいけない。**
直したらコミットし、全部緑になるまで 6〜8 を繰り返す。

## 9. セルフレビューする

`pr-reviewer` エージェントに `origin/main...HEAD` の差分を見せる。
指摘があれば直してから次へ（直したら 7〜8 をやり直す）。

## 10. PR を作る

`/ship-pr` スキルを使う。検証結果が本文に埋め込まれた PR ができる。

## 11. 報告する

ユーザーに次を伝える。

- PR の URL
- 何を実装したか
- 検証結果（成功／失敗の件数）と、テスト仕様書の場所（PR 本文に掲載済み）
- 手動で確認してほしいこと
- レビューで特に見てほしい箇所
- 意図的にやらなかったこと

## 守ること

- **工程を飛ばさない。** 急かされても、テスト監査だけは飛ばさない
- 途中で判断に迷ったら、勝手に決めずにユーザーに聞く
- PR はマージしない。マージは人間がやる
