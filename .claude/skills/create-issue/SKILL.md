# 要件をきれいな GitHub Issue にする

利用者の要件（`$ARGUMENTS`、または会話で伝えられた内容）を、**GitHub に Issue を 1 件作成する**ところまで進める。
作った Issue は、あとで `github-issue-development` スキル（`/github-issue-development <番号>`）の入力になる。
そのスキルが迷わず着手できるだけの情報（要望・背景・受け入れ条件・範囲外）がそろっていることが「きれいな Issue」の基準。

**このスキルでは実装しない。** ブランチを切らない、コードやアセットを変更しない。リポジトリは読むだけ。

## 1. 要件を整理する

利用者の言葉から、次を自分の言葉で整理する。まだ質問はしない。

- **種別**：不具合（bug）／機能追加（enhancement）／改善（enhancement）／ドキュメント（documentation）
- **何を**：対象の画面・機能・データ
- **どうしたいか**：望む状態
- **なぜ**：困っていること、目的

要望が複数混ざっていたら、**1 Issue 1 目的**に分けることを提案する（分けるかは利用者に聞く）。

## 2. リポジトリを読んで、自分で埋められることを埋める

利用者にしか分からないこと以外は、質問せずに調べる。

- `AGENTS.md`（構成・規約・「レビューで特に見る点」「テスト方針」）を読み、関係する機能の場所をつかむ
- 関係するコード・シーン・設定を読み、**現状の振る舞い**と**関係するファイル**を特定する
- 既存の Issue と PR を探し、重複や関連が無いか確かめる

```powershell
gh issue list --state all --limit 50 --search "<キーワード>"
gh pr list --state all --limit 20 --search "<キーワード>"
```

重複する Issue があれば、新しく作らずにその Issue を示して、どうするかを利用者に聞く。

- **既存の Issue に追記する**：追記する文面を見せて確認を取ってから、`gh issue comment <番号> --body-file <一時ファイル>` で追記して終わる
- **別件として作る**：違いを本文の「参考」に書いたうえで、このまま進める
- **何もしない**：既存の Issue の URL を示して終わる

## 3. 必須項目がそろっているか確かめる

次の表で、足りない項目を洗い出す。**推測で埋めない。** コードから確かめられない「利用者の意図」は必ず聞く。

| 種別 | 必須項目 |
|---|---|
| すべて | 要望（何を実現したいか）／背景（なぜ必要か）／**受け入れ条件**（完了を確かめられる形で 1 つ以上）／**範囲外・制約**（今回やらないこと、やってはいけないこと・触ってはいけない範囲。無ければ「特になし」と確認する） |
| 不具合 | 再現手順／期待する動作／実際の動作／環境（`AGENTS.md` の対象環境に合わせて聞く。例：OS・ブラウザ・端末、開発環境か本番か）／頻度（毎回か、ときどきか） |
| 機能追加・改善 | 利用者から見た振る舞い（誰が・いつ・何をすると・どうなる）／表示する文言や UI の指定があるか |

あわせて `AGENTS.md` の「レビューで特に見る点」「テスト方針」の観点で、受け入れ条件の抜けを探す
（例：失敗したときの振る舞い、保存データとの互換、境界の値、対象の端末ごとの表示）。抜けていそうなら、それも質問に含める。

## 4. 足りない情報を利用者に尋ねる

- **AskUserQuestion で、1 回に最大 4 問までまとめて聞く。** 1 問ずつ何往復もしない
- 選択肢は具体的にする。調べた結果から妥当な案があれば、先頭に置いて「(推奨)」を付ける。
  自由に書いてもらうほうがよい項目（再現手順など）は、選択肢に頼らず普通の文章で尋ねる
- 利用者が「任せる」と答えた項目は、提案した案を採用し、本文に「（提案を採用）」と書く
- 2〜3 回尋ねても決まらない項目は、利用者の了承を得て「未確定事項」として本文に残す。**黙って推測で埋めない**

## 5. 下書きを見せて確認を取る

次の形で下書きを作り、タイトル・ラベル・本文をそのまま利用者に見せる。
そのうえで AskUserQuestion で「この内容で作成する／直してから作成する」を確かめる。**確認なしに作成しない。**

**タイトル**：日本語で、何をどうするかが一目で分かる 40 字程度。「〜について」のような曖昧な書き方は避ける
（例：「ログイン直後に残り回数の表示が 1 つ多くなる」「設定画面から通知をオフにできるようにする」）

**ラベル**：`gh label list` にある既存のラベルから選ぶ（通常は `bug` か `enhancement`、手順書なら `documentation`）。
新しいラベルは作らない。担当者やマイルストーンは、指定が無ければ付けない。

**本文**（該当しない節は消す。不具合でなければ「現状」節は現在の振る舞いを短く書く）：

```markdown
## 要望
（何を実現したいか。1〜3 文）

## 背景
（なぜ必要か。困っていること、目的）

## 現状
- 再現手順：
  1. …
- 期待する動作：…
- 実際の動作：…
- 環境：…（頻度：毎回／ときどき）

## 受け入れ条件
- [ ] （完了を確かめられる形で。「〜できること」「〜と表示されること」など）
- [ ] …

## 範囲外・制約
- 範囲外：（今回やらないこと。無ければ「特になし」）
- 制約：（やってはいけないこと、触ってはいけない範囲。例：保存データの形式を変えない。無ければ「特になし」）

## 参考
- 関係しそうなファイル：`path/to/file`（調べて分かったこと）
- 関連する Issue・PR：#…

## 未確定事項
- （利用者の了承を得て残したもの。無ければ節ごと消す）
```

## 6. Issue を作成する

本文は一時ファイル経由で渡す（改行と日本語が崩れないように）。

- 一時ファイルは **Write ツールで `$env:TEMP` の下に書く**（UTF-8、BOM なし）。Windows PowerShell 5.1 の `Set-Content` は
  既定で ANSI（日本語環境では CP932）で書くので文字化けし、`Out-File -Encoding utf8` は BOM が本文の先頭に紛れ込む
- リポジトリの中には置かない（保護ブランチにいると編集前のフックが書き込みを拒否する。このスキルはブランチを切らない）
- 作成後に一時ファイルを消す

```powershell
gh issue create --title "<タイトル>" --label "<ラベル>" --body-file <一時ファイル>
```

## 7. 報告する

- 作成した Issue の URL と番号
- 着手するときは `/github-issue-development <番号>` を使えること
- 未確定事項を残した場合は、その一覧

## 守ること

- **ゴールは Issue を 1 件作成すること。** 実装・ブランチの作成・コードの変更をしない
- 利用者の確認を取らずに Issue を作成しない。作成後に内容を変える必要があれば、利用者に確認してから `gh issue edit` で直す
- Issue を閉じない、削除しない、ほかの Issue を編集しない（例外：重複する Issue への追記を利用者が選んだときに、
  確認を取った文面を `gh issue comment` で追記することだけ）
- 秘密情報（API キー、トークン）や、利用者の個人的なデータ（会話の中身など）を本文に書かない
- 本文・タイトルは日本語で書く（コードの識別子やファイル名は元のまま）
